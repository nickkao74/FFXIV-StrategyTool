# 03 — 座標轉換與圖元對照

把 BossMod 的世界座標/形狀,翻譯成本專案 `data/*.js` + `js/arena.js` 用的格式。

---

## 1. 兩套座標系

| | BossMod | 本專案 |
|---|---|---|
| 原點 | 場地中心(朱雀 = 世界 `(100, 100)`) | 場地中心 = `(0, 0)` |
| 單位 | yalm(遊戲碼) | 場地半徑 = 100 的正規化單位 |
| X 軸 | `+X` = 東 | `+x` = 東 |
| 縱軸 | `+Z` = **南** | `+y` = **南**(SVG 螢幕座標,向下) |
| 角度 0° | **南** | **北** |
| 角度正向 | 順時針 | 順時針 |

**兩邊的 X/Y 軸方向剛好一致**(因為 SVG 的 y 向下,恰好等於世界的 +Z 向南),
所以位置轉換是純粹的平移 + 縮放,不需要翻轉。

## 2. 轉換公式

```js
// 場地參數(每個副本不同,從 module 主類別的 ArenaCenter / Bounds 讀)
const CENTER = { x: 100, y: 100 };  // WPos(100, 100)
const RADIUS_YALM = 20;             // 用於正規化的名目半徑
const K = 100 / RADIUS_YALM;        // = 5,「1 yalm = 5 個我們的單位」

// 位置
ourX = (world.X - CENTER.x) * K;
ourY = (world.Z - CENTER.y) * K;

// 長度 / 半徑
ourR = yalm * K;

// 角度(BossMod 0°=南 → 我們 0°=北)
ourDeg = (180 - bossmodDeg + 360) % 360;
```

### 角度公式的驗證

| BossMod | 方位 | `180 − θ` | 我們的方位 | ✓ |
|---:|---|---:|---|---|
| `0°` | 南 | `180°` | 南 | ✓ |
| `90°` | 東 | `90°` | 東 | ✓ |
| `180°` | 北 | `0°` | 北 | ✓ |
| `−90°` | 西 | `270°` | 西 | ✓ |
| `+135°`(SongOfFire) | 東北 | `45°` | 東北 | ✓ |
| `+45°`(SongOfSorrow) | 東南 | `135°` | 東南 | ✓ |
| `−45°`(SongOfOblivion) | 西南 | `225°` | 西南 | ✓ |
| `−135°`(SongOfDurance) | 西北 | `315°` | 西北 | ✓ |

後四列是與 `data/hells-kier-ex.js` 既有的四色地板資料做的交叉驗證,詳見 `04`。

### 名目半徑的注意事項

朱雀的 `Phase1Bounds` 是 `Polygon(center, 19.5f, 80)`,但 `Phase2Bounds` 的外緣是 `20f`,
場地標記(A/B/C/D)在我們的資料裡放在 `±95`。

實務上 **取 `RADIUS_YALM = 20`**(外緣),此時:

- 天坑 r=3.5 → 我們的 `17.5`
- P1 場地邊界 19.5 → 我們的 `97.5`(所以標記放 95 是合理的)

若某副本的 Bounds 是不規則多邊形,就取其外接圓半徑,並在該副本的資料檔頂端註明。

## 3. AOEShape → `js/arena.js` 圖元對照

`arena.js` 目前 `_drawAoe()` 支援的 `type`:
`circle` / `donut` / `cone` / `blackhole` / `tentacle` / `quadrant` / `hole` / `tower` /
`feather` / `bird` / `xmark` / `arrow` / `charStrip` / `arcArrow` / `text` / `knockback` /
`share` / `triangle` / `target`。

| BossMod | 我們的寫法 | 備註 |
|---|---|---|
| `AOEShapeCircle(r)` | `{ type:'circle', x, y, r: r*K }` | 直接對應 |
| `AOEShapeDonut(ri, ro)` | `{ type:'donut', rInner: ri*K, rOuter: ro*K }` | 直接對應 |
| `AOEShapeCone(r, half)` + `rotation` | `{ type:'cone', r: r*K, angle: 180-rot, spread: half*2 }` | **`spread` 是總張角,要 ×2** |
| `AOEShapeDonutSector` | — | **尚無對應圖元** |
| `AOEShapeRect(front, halfW)` | — | **尚無對應圖元**(見下方缺口) |
| `AOEShapeCross(len, halfW)` | — | **尚無對應圖元** |
| `AOEShapeCapsule` | — | 尚無;可用 `circle` + `charStrip` 近似 |
| `GenericTowers.Tower(pos, r)` | `{ type:'tower', x, y, r: r*K }` | 直接對應 |
| `SpreadFromIcon(r)` | `{ type:'circle', color:'…' }` 或既有的紅圈畫法 | |
| `StackWithIcon(r)` | `{ type:'share', x, y }` | |
| `SimpleKnockbacks(dist, kind)` | `{ type:'knockback', … }` | `Kind.TowardsOrigin` = 牽引,箭頭反向 |
| `GenericForcedMarch` | `{ type:'arrow', … }` | 方向 = `AddForcedMovement` 的 `dir` |
| 朱雀四象限地板 | `{ type:'quadrant', quad:'ne'|'se'|'sw'|'nw' }` | 專屬圖元,已存在 |

### `rect` 圖元(已實作)

朱雀的 **敗走(55×6)** 與 **井宿焰(41×20)** 都是 `AOEShapeRect`,
原本 `arena.js` 沒有對應圖元,只能拿窄扇形硬湊 —— 而扇形會讓人誤以為
「離遠一點就變窄」,實際上長方形的寬度從頭到尾一樣。已補上:

- `js/arena.js` 的 `_drawAoe()` 加 `case 'rect'`
- `js/board/import.js` 把它換算成白板既有的 `aoe-rect`(中心 + 寬高 + 旋轉),
  支援吸附兵棋。白板端不需要新增物件種類。

> ⚠️ 新增任何圖元前,先讀專案的 `board-object-parity` skill ——
> 只在 `arena.js` 加 case 而沒有同步 `js/board/`,白板匯入時會靜默丟棄該圖元。

`rect` 的規格刻意對齊 BossMod 語意,避免轉換時再做心算:

```js
{ type: 'rect',
  x, y,              // 原點(= BossMod 的 origin,不是矩形中心)
  lengthFront,       // 原點往 angle 方向的長度
  lengthBack = 0,    // 原點往反方向的長度
  halfWidth,         // 半寬
  angle }            // 我們的角度慣例(0=北)
```

## 4. 從 module 抽資料的機械流程

1. 開 `<Module>.cs` 主檔 → 抄 `ArenaCenter`、`Bounds`,決定 `RADIUS_YALM` 與 `K`。
2. 開 `<Module>Enums.cs` → 抄 OID/AID 表。**AID 的註解裡通常已經寫了形狀與尺寸**
   (例:`// Boss->self, 4s cast, range 41 width 20 rect`),可先當索引,但 **以程式碼裡實際的
   `new AOEShape…` 為準**,註解偶有過時。
3. 全檔搜尋 `new AOEShape` 與 `new AOEInstance` → 得到所有幾何。
4. 全檔搜尋 `AddForbiddenZone` / `GoalZones` / `ForbiddenDirections` → 得到 **安全區解法**。
5. 開 `<Module>States.cs` → 累加 `delay` 得到時間軸;抽出被抽成私有方法的段落當「組合技」。
6. 套用第 2 節公式轉座標,依第 3 節表格轉圖元,寫進 `data/<raid>.js`。
